    Overview

    Build Social Spark

    An ADK agent that turns an idea into a researched, on-brand, illustrated social post, approved by you, then published for real, all wrapped in a web app you didn't have to build.

    Theory — this is Google's "Build" pillar

    Google Cloud's Gemini Enterprise Agent Platform groups agent work into four pillars: Build, Scale, Govern, Optimise. This lab is Build — designing and composing an agent: the Agent Development Kit (ADK) itself, Model Garden (the Gemini models your agents call), function tools, Agent Skills, and MCP toolsets. Multi-agent decomposition (an orchestrator routing to specialist sub-agents) and connecting an Agent Garden template or a RAG Engine-backed memory agent are Build-pillar concepts too — you'll see the fuller version of that in the tagged reference (below). None of what you build today is about where it runs (that's Scale), who's allowed to do what (that's Govern), or whether it's any good (that's Optimise) — those are Labs 2–4 in this series.

    How this lab works

    Every step has three parts: the concept, a prompt you can give your coding agent (Antigravity, Claude Code or Gemini CLI — the starter repo's AGENTS.md tells it the project conventions), and a checkpoint that proves the step worked. The code blocks are there to read and compare against, or to type by hand if you prefer; the checkpoint is what counts, not matching the code. Review your agent's plan before accepting it. One step, marked clearly, is designed to fail the first time.

    Today you write a real ADK backend: an orchestrating agent with a hand-written tool, four Agent Skills (you author one yourself), an isolated research sub-agent, and a live MCP connection to Buffer that actually publishes what you approve. Then you wire up a CopilotKit frontend that's given to you, but you'll open the two files that make it talk to ADK, because that connection is the whole point of Step 8.

    Step 4 of 9⏱ 15 min

    Teach it Agent Skills

    A Skill is a folder with a SKILL.md file: YAML frontmatter (name, description) plus markdown instructions. The agent decides when to load one via a tool call; the content isn't in the system prompt until it's actually needed. That's progressive disclosure: keep the default context small, pull in detail only when relevant.

    Why skills matter
    • The default prompt stays small. Only each skill's name and one-line description are always in context. The full rules load when a draft needs them, so adding a fifth or a tenth skill costs about a line each until it is used.
    • Behaviour lives in files, not code. Tone, structure and platform rules are markdown. Anyone can change them, review the change in a pull request, and never open agent.py.
    • Each concern stays separate. One long instruction prompt makes rules crowd each other. A skill keeps formatting, platform rules, tone and image style apart, and the agent picks what applies.
    • A skill is just a folder. You can copy one into another agent or project.
    • It is governance you can read. A skill is a reviewable file that constrains what the agent writes. Lab 3 comes back to this.
    Ask your coding agent

    Create skills/brand-voice/SKILL.md with frontmatter name: brand-voice and a description saying to load it whenever drafting, then tone rules (casual, British English, short sentences) and a banned-clichés list. Then build a SkillToolset with load_skill_from_dir for post-formatter, platform-style, brand-voice and poster-style from the skills/ folder at the repo root, add it to root_agent's tools, and update the instruction to load the relevant skills before drafting and the poster-style skill before generating an image.

    Open the three skills you copied in and read them; that's the whole format:

    • skills/post-formatter/SKILL.md — structural rules (hook line, paragraph limits, hashtags)
    • skills/platform-style/SKILL.md — points at a second-level reference file per platform (references/linkedin.md, references/x.md)
    • skills/poster-style/SKILL.md — visual style rules for generate_image prompts (you'll wire this in properly once images route through the skill)

    Now write one yourself: brand-voice

    Create skills/brand-voice/SKILL.md:

    skills/brand-voice/SKILL.md
    ---
name: brand-voice
description: Tone-of-voice and language rules for all written content. Load whenever drafting or revising a post.
---

# Brand Voice

## Tone
- Casual and warm, like explaining something interesting to a colleague.
- British English throughout: organise, colour, whilst, learnt.
- Short sentences. Active voice.

## Banned clichés
Never use: "game-changer", "unlock the power of", "seamless", "leverage"
(as a verb), "I'm thrilled to announce".
    Gotcha

    The name: in the frontmatter must exactly match the directory name, or loading it raises an error. brand-voice/ ↔ name: brand-voice.

Workflow:

   brand-voice (tone).

    Step 5 of 9⏱ 10 min

    Add web research (and a real ADK constraint)

    Add google_search, a built-in tool, so the agent can ground drafts in real facts. This step is designed to fail first. You'll hit a real Agent Platform constraint, read the error, and fix it the idiomatic ADK way.

    Ask your coding agent

    Part 1, the naive version: add ADK's built-in google_search tool directly to root_agent's tools list, next to the existing tools. Run it and read the error. Part 2, the fix: move google_search into its own Agent named web_researcher that returns a concise factual summary, expose it to root_agent through AgentTool, and update the workflow instruction to research first when the idea needs facts.

    Part 1: the naive version (this will fail, on purpose)

    backend/social_poster/agent.py (attempt 1)
    from google.adk.tools import google_search

root_agent = Agent(
    # ...everything from Step 4 unchanged...
    tools=[google_search, generate_image, skill_toolset],
)

    Restart adk web and ask for a post that needs facts. Read the error before you touch anything.

    What you'll see, and why

    Agent Platform rejects a single model call that mixes google_search with your own function tools: "Multiple tools are supported only when they are all search tools." The model is not broken and neither is your code; the platform enforces that built-in search runs alone. The fix: isolate search in its own agent, and expose that agent to the root agent as a tool via AgentTool. This is the idiomatic ADK pattern for "a tool that needs tools of its own", and it is your first multi-agent split.

    Part 2: the fix

    backend/social_poster/agent.py
    from google.adk.tools import google_search
from google.adk.tools.agent_tool import AgentTool

search_agent = Agent(
    name="web_researcher",
    model="gemini-flash-latest",
    description="Researches facts, dates, and context on the web.",
    instruction="Research the given query and return a concise summary of relevant facts.",
    tools=[google_search],
)

root_agent = Agent(
    name="social_poster",
    model="gemini-flash-latest",
    description="Helps the user turn an idea into a polished social media post.",
    instruction="""You help the user turn an idea into a social media post.

Workflow:
1. If the idea needs facts, dates, or context, research it with the
   web_researcher tool first.
2. When drafting, load and follow the relevant skills: post-formatter
   (structure), platform-style (rules for the target platform), and
   brand-voice (tone).
3. If the user asks for an image, load and follow the poster-style skill,
   then call generate_image with a detailed visual description and tell
   them where the file was saved.""",
    tools=[AgentTool(agent=search_agent), generate_image, skill_toolset],
)

    Run the full flow: idea → research → skills → draft → image, all in one conversation. This is a complete, standalone agent; everything below adds real publishing.

    Checkpoint

    First run: the error above appears — that's the point. After the fix: the Trace shows web_researcher as a tool call on social_poster, with google_search inside it, and the draft uses facts from the research.

    Step 6 of 9⏱ 20 min

    Publish for real: Buffer + the approval gate

    So far every tool has been Python running in-process. MCP (Model Context Protocol) is a standard for connecting to tools that live in a separate process: could be someone else's server, any language, doesn't need to know anything about ADK. Buffer runs one at https://mcp.buffer.com/mcp — no server for you to write or copy, just a key and a URL.

    Ask your coding agent

    Add an McpToolset connected to Buffer's remote MCP server at https://mcp.buffer.com/mcp over StreamableHTTP, sending a Bearer token read from the BUFFER_API_KEY environment variable, with require_confirmation=True. Add it to root_agent's tools. Add strict posting rules to the instruction: always show the finished draft and get explicit approval before any posting action, and for an immediate post ask Buffer to publish now rather than schedule.

    1. Connect a Buffer account

    1. Create or log into a free Buffer account, and connect at least one channel (LinkedIn is fine to test with; Buffer authenticates to each platform on its own side).
    2. Get an API key: open publish.buffer.com/settings/api, choose Buffer AI → New Key, name it, and copy it now (you may not be able to see it again). Stuck? Buffer's how-to with screenshots.
    3. Add it to backend/social_poster/.env: BUFFER_API_KEY=...
    Gotcha: text only

    Buffer's create_post must be text only. Buffer's servers can't fetch a locally-generated image file; confirmed live: "Invalid post: Image could not be read from its URL." If the user wants an image with a Buffer post, generate it for the local gallery only and say so; images only travel with LinkedIn's own tool (Step 7).

    2. Wire the toolset in, with the approval gate

    backend/social_poster/agent.py
    import os
from google.adk.tools.mcp_tool import McpToolset
from google.adk.tools.mcp_tool.mcp_session_manager import StreamableHTTPConnectionParams

BUFFER_API_KEY = os.environ.get("BUFFER_API_KEY", "")

buffer_toolset = McpToolset(
    connection_params=StreamableHTTPConnectionParams(
        url="https://mcp.buffer.com/mcp",
        headers={"Authorization": f"Bearer {BUFFER_API_KEY}"},
    ),
    # Framework-level approval gate: see below, not just an instruction.
    require_confirmation=True,
)

    Add it to root_agent's tools=[...] list, and update the instruction with a posting rule:

    backend/social_poster/agent.py (instruction excerpt)
        instruction="""... (steps 1-3 from before) ...

4. ALWAYS show the finished draft to the user and ask for their approval
   before any posting action. For an immediate post, ask Buffer to publish
   now rather than schedule.

Posting rules (strict):
- Only post AFTER the user has explicitly approved the exact draft shown to
  them. "Yes", "post it" counts; enthusiasm about the idea does not.
- After posting, share the returned confirmation with the user.""",
    tools=[AgentTool(agent=search_agent), generate_image, skill_toolset, buffer_toolset],

    Why require_confirmation, not just an instruction

    Right now the instruction text says "ask before posting", but that's a suggestion, not a guarantee. require_confirmation=True is code-level: ADK pauses any call into this toolset and forces an explicit ToolConfirmation before the call actually executes, no matter what the model decides on its own.

    Restart and try: draft → Yes, post it. Nothing fires until you approve inside adk web's confirmation control; try rejecting once too, and confirm the post never goes out.

    The gate covers every tool in the toolset

    require_confirmation=True applies to all of Buffer's tools, so listing channels will ask for approval too. That is fine for today. The reference build splits Buffer into two toolsets with tool_filter, one read-only and one gated, so only create_post pauses; try that yourself once the golden path works.

    Real posts, no dry-run

    Unlike LinkedIn (Step 7), Buffer has no DRY_RUN flag. A "scheduled" post is real and will publish later on whatever channel is connected: require_confirmation=True above is the actual safety net here, not a simulation.

    Checkpoint

    Say Yes, post it. adk web shows a confirmation control before anything reaches Buffer. Reject once: nothing appears in Buffer. Approve once: Buffer's response comes back and the post is in your Buffer queue.

    Step 7 of 9 · Optional⏱ 15 min

    Bonus: add LinkedIn as a second publisher

    Buffer covers scheduling and multi-platform posting. LinkedIn's own API adds one thing Buffer can't: an immediate post with an image attached. This step is entirely optional; skip to Step 8 if you're short on time.

    Ask your coding agent

    Add a second McpToolset that launches mcp/linkedin_server.py over stdio using the current Python interpreter, passing DRY_RUN and LINKEDIN_ACCESS_TOKEN through from the environment, filtered to get_profile and create_post, with require_confirmation=True and tool_name_prefix="linkedin" (so its tools don't clash with Buffer's create_post). Add a POST_VIA environment switch (buffer, linkedin, or blank for both) that decides which toolsets are attached, and add routing guidance to the instruction: LinkedIn for an immediate post with an image, Buffer for scheduling or other platforms.

    1. Read the given LinkedIn MCP server

    The starter repo already contains mcp/linkedin_server.py: a FastMCP server with two tools, get_profile and create_post. Open it and find the line where DRY_RUN short-circuits the real LinkedIn API call — that flag is what makes this step safe to run.

    2. Get an access token

    1. Create a LinkedIn Developer app: linkedin.com/developers/apps → Create app (needs a company page; a dummy one is fine).
    2. Add products: Share on LinkedIn (grants w_member_social) and Sign In with LinkedIn using OpenID Connect (grants openid profile), both instant self-serve.
    3. Fastest path to a token: the OAuth Token Generator in the Developer Portal: select your app, check all scopes, Request access token, copy it straight in.
    backend/social_poster/.env
    DRY_RUN=true
LINKEDIN_ACCESS_TOKEN=...
    Keep DRY_RUN=true

    With DRY_RUN=true (the default), the server logs the payload and returns a fake URL; nothing touches LinkedIn. Only flip it for a single deliberate happy-path check, then flip it straight back.

    3. Wire both toolsets in with routing

    backend/social_poster/agent.py
    import sys
from google.adk.tools.mcp_tool.mcp_session_manager import StdioConnectionParams
from mcp import StdioServerParameters

PROJECT_ROOT = pathlib.Path(__file__).resolve().parents[2]
MCP_SERVER = PROJECT_ROOT / "mcp" / "linkedin_server.py"

linkedin_toolset = McpToolset(
    connection_params=StdioConnectionParams(
        server_params=StdioServerParameters(
            command=sys.executable,
            args=[str(MCP_SERVER)],
            env={
                "DRY_RUN": os.environ.get("DRY_RUN", "true"),
                "LINKEDIN_ACCESS_TOKEN": os.environ.get("LINKEDIN_ACCESS_TOKEN", ""),
            },
        ),
    ),
    tool_filter=["get_profile", "create_post"],
    # Buffer's server also has a create_post; Gemini rejects two functions with
    # the same name. The prefix renames these to linkedin_get_profile and
    # linkedin_create_post. The filter above still uses the original names.
    tool_name_prefix="linkedin",
    require_confirmation=True,
)

# POST_VIA overrides the LLM's own routing: "buffer" drops the LinkedIn
# tool entirely, "linkedin" drops Buffer even if a key is set. Blank
# exposes both and lets the agent route by what the user asks for.
POST_VIA = os.environ.get("POST_VIA", "").strip().lower()
use_linkedin = POST_VIA != "buffer"
use_buffer = bool(BUFFER_API_KEY) and POST_VIA != "linkedin"
    Why the prefix matters

    Buffer's remote server and the LinkedIn server both expose a tool called create_post. Without a rename, every turn fails with "Duplicate function declaration found: create_post", because Gemini rejects two functions with one name. tool_name_prefix="linkedin" renames LinkedIn's tools to linkedin_get_profile and linkedin_create_post; the call to the LinkedIn server still uses the original name. POST_VIA is now just an optional override.

    Add the routing guidance to the instruction (choose LinkedIn for an image-carrying immediate post, Buffer for scheduling or other platforms), and add linkedin_toolset to tools=[...] alongside buffer_toolset. Both still gate through require_confirmation=True: same mechanism, two publishers.

    Restart and try: ask specifically for an immediate LinkedIn post with an image, then ask to schedule something for next week; watch it pick a different tool each time.

    Checkpoint

    With POST_VIA=linkedin, an immediate post with an image routes to LinkedIn's linkedin_create_post and the DRY_RUN log shows the payload. With POST_VIA=buffer, the same request goes to Buffer. With both active and POST_VIA blank, the agent picks by what you ask for, and there is no duplicate-declaration error. If you see one, the tool_name_prefix is missing.

    Connection point 1: the AG-UI bridge (given: read this one)

    This is short, and it's the entire reason Step 8 exists: exposing the exact same root_agent object over HTTP.

    backend/main.py
    """AG-UI bridge: exposes the social_poster agent to the CopilotKit frontend.

Run from the repo root:  uv run uvicorn backend.main:app --port 8000
"""

import pathlib

from ag_ui_adk import ADKAgent, add_adk_fastapi_endpoint
from dotenv import load_dotenv
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from fastapi.staticfiles import StaticFiles

load_dotenv(pathlib.Path(__file__).parent / "social_poster" / ".env")

from backend.social_poster import db  # noqa: E402  (needs .env first)
from backend.social_poster.agent import root_agent  # noqa: E402  (needs .env first)

app = FastAPI(title="social-agent AG-UI backend")

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_methods=["*"],
    allow_headers=["*"],
)

adk_agent = ADKAgent(
    adk_agent=root_agent,
    app_name="social_poster",
    user_id="devcamp-user",  # single-user POC; extract from auth in real apps
)

add_adk_fastapi_endpoint(app, adk_agent, path="/api/adk")

# Serve generate_image's output files so the frontend's image gallery
# (PostGallery.tsx) can render them — tools.py writes local file paths, which
# the browser has no way to read directly otherwise.
GALLERY_DIR = pathlib.Path(__file__).resolve().parents[1] / "gallery"
GALLERY_DIR.mkdir(parents=True, exist_ok=True)
app.mount("/outputs", StaticFiles(directory=GALLERY_DIR), name="outputs")


@app.get("/healthz")
def healthz() -> dict:
    return {"status": "ok"}


@app.get("/api/posts")
def posts() -> dict:
    """Published posts (with whatever image they used), read from the local
    SQLite store — durable across reloads/restarts, unlike ADK session state
    or the browser's own chat history."""
    return {"posts": db.list_posts()}

    That's the whole bridge, plus a health check and the /api/posts route the post gallery reads. root_agent is imported unchanged from the agent.py you spent the last six steps writing.

    Connection point 3: publish the pipeline stage (you write this one too)

    That shared pipeline_stage value has to come from somewhere: three small callbacks on root_agent that write it into session state as the run progresses. Nothing else in the agent changes.

    backend/social_poster/agent.py (add above root_agent)
    from typing import Any, Optional
from google.adk.agents.callback_context import CallbackContext
from google.adk.tools.base_tool import BaseTool
from google.adk.tools.tool_context import ToolContext

# idea -> researching -> drafting -> awaiting_approval -> posted
_TOOL_STAGES = {
    "web_researcher": "researching",
    "load_skill": "drafting",
    "generate_image": "drafting",
}


def _init_stage(callback_context: CallbackContext) -> None:
    if "pipeline_stage" not in callback_context.state:
        callback_context.state["pipeline_stage"] = "idea"


def _track_stage(
    tool: BaseTool, args: dict[str, Any], tool_context: ToolContext, tool_response: dict
) -> Optional[dict]:
    if tool.name in _TOOL_STAGES:
        tool_context.state["pipeline_stage"] = _TOOL_STAGES[tool.name]
    elif tool.name in ("create_post", "linkedin_create_post") and tool_response.get("isError") is False:
        tool_context.state["pipeline_stage"] = "posted"  # only a completed MCP call
    return None  # never modify the tool result


def _stage_after_agent(callback_context: CallbackContext) -> None:
    # A turn that ends mid-pipeline is waiting on the user (draft approval).
    if callback_context.state.get("pipeline_stage") in ("researching", "drafting"):
        callback_context.state["pipeline_stage"] = "awaiting_approval"
    backend/social_poster/agent.py (root_agent, three new arguments)
    root_agent = Agent(
    # ...name, model, description, instruction, tools as before...
    before_agent_callback=_init_stage,
    after_tool_callback=_track_stage,
    after_agent_callback=_stage_after_agent,
)
